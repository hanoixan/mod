# System: mod

`mod` is a minimalist, full-screen terminal text editor that edits a single file at a time. It opens files of any size without loading them into memory, keeps an unlimited branching undo history in a portable `<file>.history` sidecar, shows line numbers, supports regex find/replace, styles Markdown in place, and can color other languages using Language Server Protocol (LSP) semantic tokens. It has an Alt-key menu bar (File, Edit, View, Options, Help), the common Ctrl-key shortcuts (which the user can change), and an undo-history panel for navigating the branched history.

## Scope

In scope:

- Editing several files in one process (`mod [PATH...]`), one shown at a time: each path, and each File > Open, opens a document; the Documents menu (Alt+D) switches between them and File > Close closes the shown one. With no path, `mod` starts with an untitled buffer for starting a new file; its first save is a Save As.
- Files larger than RAM. The original file is memory-mapped and never copied wholesale.
- An unlimited undo **tree**. Editing after an undo creates a sibling branch, so nothing is discarded. By default the tree is kept in memory for the session only; checking **Persist History** in the Undo History pane persists it continuously to `<file>.history` (and an existing, loadable `<file>.history` turns that on when the file is opened). A documented format lets any user or tool load it. A tree-view panel ([HistoryView](./src/ui/history_view.hpp.skel.md#class-historyview), Edit > Undo History…) shows the whole branched history in a side pane beside the text and continues editing from any chosen node. It is opened from the Edit menu only; it has no key. Two commands at the bottom of that panel manage the history as a whole: Clear History… (C) deletes the sidecar and starts a new history, and Trim History… (P) deletes the history older than a number of days the user enters and rewrites the sidecar smaller. They are in no menu. The same question is offered whenever loading a sidecar takes more than 5 seconds; see [Document.prune_history](./src/edit/document.hpp.skel.md#function-prune_history).
- A line-number gutter, regex search and replace, Markdown styling, syntax coloring in two layers (a built-in, language-neutral syntax layer for keywords, strings, comments and numbers, described per language as data in `languages.json`, with a language server's semantic tokens drawn over it), configurable colors (Options > Colors…), and optional word wrap.
- A help screen (F1): the user manual ([docs/manual](./docs/manual/index.md.skel.md)) shown read-only in the document's place, with its links followed as in read-only mode and a search of every page that keeps its query and results for the session.
- A read-only mode (View > Read Only) for reading a document without changing it: in Markdown files Tab moves between links and Enter follows them, showing the target in place, and Ctrl+Left / Ctrl+Right walk back and forward through the places visited.
- A menu bar at the top of the screen, hidden until Esc (or F10, or Alt+X) shows it, after which each menu's and item's underlined letter picks it (`Esc F X` exits), with its menus opening downward; Esc three times, each within 250 ms of the one before, quits; a status line whose center carries notifications, and `Esc h: help` when there are none; plus the default key bindings listed in [Keymap](./src/app/keymap.hpp.skel.md#class-keymap): the requested ones, and Ctrl+Q quit, Ctrl+X cut, F3 / Shift+F3 find next / previous, Ctrl+G go to line, Ctrl+K cut to the end of the line, Ctrl+T suspend (stop as a shell job; Ctrl+Z stays Undo). Save As has no default key.
- User-configurable key bindings: Options > Key Bindings… lists every command with its keys, filters the list as you type, and adds, removes and resets keys ([KeymapView](./src/ui/keymap_view.hpp.skel.md#class-keymapview)). The user's changes, and only those, are stored under `keymap` in `settings.json`.
- CMake builds for Linux and macOS. Linux is the reference platform. Windows builds will use the MSYS2 MSYS environment, but no Windows build is made in this phase; see the Windows decision below.

Out of scope (not requested, so not designed): splits (several documents on screen at once), mouse support, plugins, text encodings other than UTF-8 (other bytes are preserved but shown escaped), terminfo-driven terminal capability detection, LSP features other than semantic tokens (no completion, diagnostics, hover), and grammar engines for the syntax layer (no TextMate grammars, no tree-sitter): the syntax layer is the small, data-driven [SyntaxHighlighter](./src/syntax/syntax_highlighter.hpp.skel.md#class-syntaxhighlighter).

## Glossary

- **Original buffer**: a read-only memory mapping of a file on disk (the opened file, a previously saved version of it, or the sidecar's payload area).
- **Add buffer**: an append-only, in-memory byte store that holds every byte typed or pasted during the session.
- **Piece / piece tree**: a document is a sequence of *pieces* `(buffer, offset, length)` kept in a balanced tree. Each node is augmented with byte length and line-feed count. See [PieceTree](./src/text/piece_tree.hpp.skel.md#class-piecetree).
- **Chunk**: a fixed-size slice of an original buffer (default 1 MiB, with hard boundaries, so a line may straddle two chunks; seeding reads no file bytes). The tree is seeded with one piece per chunk so a background scan can fill in line counts chunk by chunk.
- **Edit op**: one primitive, self-contained, invertible change `(offset, deleted bytes, inserted bytes)`. See [EditOp](./src/edit/undo_tree.hpp.skel.md#symbol-editop).
- **Undo node**: one user-level action, made of one or more edit ops (a typing burst, a paste, a replace-all). Nodes form a tree rooted at the file's state when history began.
- **Branch**: a node with more than one child. Redo follows the node's *preferred child*, which is the most recently created or visited one.
- **Save point**: an undo node whose resulting content was written to disk, recorded with the file's size and content hash.
- **Sidecar**: the `<file>.history` file next to the edited file. It holds the persisted undo tree. See [sidecar format](./docs/sidecar-format.md.skel.md).
- **Style**: a semantic text class (heading, emphasis, keyword, …) produced by a highlighter. The theme maps it to terminal attributes.

## Global decisions

- **Language:** C++23, limited to the subset that GCC 13 (`g++-13`, verified 13.4 on the build machine) and current AppleClang support. MSVC is not a target: Windows builds will use the GCC toolchain of the MSYS2 MSYS environment. Allowed: `std::expected`, `<format>` (`std::format`, `std::format_to`), `std::span`, `std::move_only_function`, `std::to_underlying`, `std::unreachable`, `std::byteswap`, `std::views::zip/chunk/enumerate`, `if consteval`, multidimensional `operator[]`, static `operator()`. Forbidden (absent in GCC 13): `<print>`, `<generator>`, `<flat_map>`, `<mdspan>`, `std::ranges::to`, explicit object parameters ("deducing this"). Avoid `<stacktrace>`, because it needs an extra link library. C++20 modules are not used (ninja 1.10 and GCC 13 cannot scan them); every unit is a `.hpp`/`.cpp` pair.
- **Code conventions:** all code lives in `namespace mod`. Include paths are rooted at `src/` (`#include "util/error.hpp"`), and test sources may also include files from `tests/`. Files carry no reference to the skel tree: each stand-in records in its front matter (`stamp: source <hash>, stand-in <hash>`) that it and its file agreed when last stamped, and `skel_check.py status` reports which side has moved since. Enumerators and functions use `snake_case` names as written in the stand-ins.
- **Build:** CMake ≥ 3.25 with the Ninja generator. On the build machine the compiler must be selected explicitly as `g++-13`, because `/usr/bin/g++` is 11.4 and lacks `<expected>`. See [CMakePresets](./CMakePresets.json.skel.md).
- **Distribution:** no packaging (no CPack, deb, rpm, Homebrew or winget). `cmake --install` places the binary, the user manual ([docs/manual](./docs/manual/index.md.skel.md), plain Markdown with relative links, the authoritative user documentation) and a reference `settings.json` generated from the settings schema under `<prefix>/share/mod`. On Linux the binary links libstdc++ statically (`-static-libstdc++`) so that it runs on a stock Ubuntu 22.04; glibc stays dynamic, so release binaries are built on 22.04. See [CMakeLists.txt](./CMakeLists.txt.skel.md).
- **Platform:** POSIX.1-2008 (termios, `poll`, `mmap`, `posix_spawn`, `rename`) on Linux, macOS and the MSYS2 MSYS environment. All OS calls go through `src/platform/`. Only 64-bit targets are supported, because files of any size need a 64-bit address space for mapping.
- **Windows:** Windows builds use the **MSYS environment** of MSYS2, the POSIX-emulating one that links against `msys-2.0.dll` (a Cygwin-derived layer). The `src/platform/*_posix.cpp` backends build there unchanged, so there are no Windows-specific backends and no `*_win32.cpp` files. The binary needs `msys-2.0.dll` at run time. No Windows build is made in this phase: there is no Windows preset, no Windows CI job, and no Windows-specific CMake logic. Not yet verified under MSYS, and to be checked when a Windows build is made: `fsync` on a directory descriptor, `rename` over a file that this process still maps, and `flock` on the sidecar, all of which go through the Cygwin layer's emulation.
- **Third-party dependencies:** exactly two, both fetched with CMake `FetchContent` at pinned versions: [PCRE2](https://github.com/PCRE2Project/pcre2) for regex search ([Regex](./src/search/regex.hpp.skel.md#class-regex)) and [doctest](https://github.com/doctest/doctest) for tests ([tests/CMakeLists.txt](./tests/CMakeLists.txt.skel.md)). Nothing else is fetched, vendored or found with `find_package` (apart from `Threads`). JSON is hand-written ([Json](./src/syntax/json.hpp.skel.md#class-json)), and so is the SHA-256 content hash ([hash](./src/util/hash.hpp.skel.md)), as portable code with no hardware acceleration.
- **Terminal model:** two behaviors, chosen by the `terminal_mode` setting or detected ([terminal_output](./src/platform/terminal_output.hpp.skel.md)). `xterm`, for xterm-compatible terminals (Windows Terminal, conhost with VT enabled, macOS Terminal/iTerm2, GNOME/Konsole/kitty/alacritty, tmux/screen): the alternate screen (`?1049`), bracketed paste (`?2004`), SGR attributes, and the 16 ANSI colors only, so the editor follows the user's terminal palette. `vt100`: strict VT100 escape codes, with bold, underline, blink and reverse and no color. Every escape code mod writes comes from that module. Colors are a [theme](./src/ui/theme.hpp.skel.md) of color specs over those 16 colors, with defaults the user can override per style in `settings.json` or the Colors editor. No terminfo or ncurses. Copies of up to 100 KB are also sent to the terminal clipboard with OSC 52; the internal clipboard is always used, and no external clipboard tool is ever run ([Clipboard](./src/edit/clipboard.hpp.skel.md#class-clipboard)).
- **Concurrency model:** one main thread owns all document, undo, view and UI state and runs the event loop in [App.run](./src/app/app.hpp.skel.md#function-run). Workers never touch that state. They post closures to [EventQueue](./src/util/event_queue.hpp.skel.md#class-eventqueue), which wakes the loop through [Terminal.wake](./src/platform/terminal.hpp.skel.md#function-wake). The workers are: one [LineScanner](./src/text/line_scanner.hpp.skel.md#class-linescanner) thread, one sidecar payload-writer thread in [Sidecar](./src/edit/sidecar.hpp.skel.md#class-sidecar), and a reader thread and a writer thread per running language server in [LspClient](./src/syntax/lsp_client.hpp.skel.md#class-lspclient); a server is shared by the open documents of one language and project ([LspServerPool](./src/syntax/lsp_pool.hpp.skel.md#class-lspserverpool)). Workers may read only immutable data: mapped original buffers and frozen add-buffer prefixes.
- **Error policy:** recoverable failures return [Result](./src/util/error.hpp.skel.md#symbol-result) (`std::expected<T, Error>`). Exceptions are not used for control flow. Anything that escapes to `main` restores the terminal before exiting with status 1. Fatal signals restore the terminal and then re-raise. A failure in an optional subsystem (sidecar, LSP, Markdown) degrades that feature and shows a status-line message. It never blocks editing or saving.
- **Logging:** off by default. If the environment variable `MOD_LOG` names a file, [log](./src/util/log.hpp.skel.md#function-log) appends timestamped lines to it. Never log to the terminal.
- **Text model:** bytes are UTF-8. Invalid bytes are preserved exactly and displayed as `\xNN`. A line break is LF. CR immediately before an LF is hidden and kept. Enter inserts the line ending found first in the file (LF if none). Text pasted from the terminal gets that same line ending for each of its line breaks, whether the terminal sent CR, LF or CR LF ([Editor.paste_text](./src/edit/editor.hpp.skel.md#function-paste_text)). Cursor movement and deletion work on **extended grapheme clusters** as defined by Unicode Standard Annex #29 for the Unicode version pinned in [width_table.inc](./src/text/width_table.inc.skel.md), so Left, Right, Backspace and Delete never split an emoji ZWJ sequence, a flag, a base character from its combining marks, or a CR from its LF. A cluster is capped at 32 code points ([MAX_CLUSTER_CODE_POINTS](./src/text/utf8.hpp.skel.md#symbol-max_cluster_code_points)); a longer run is split at the cap. Boundaries come from [next_grapheme_boundary](./src/text/utf8.hpp.skel.md#function-next_grapheme_boundary) and [prev_grapheme_boundary](./src/text/utf8.hpp.skel.md#function-prev_grapheme_boundary). Display width is still computed per code point by [display_width](./src/text/utf8.hpp.skel.md#function-display_width), and a cluster's width is the sum of its code points' widths.
- **Long lines:** by default a long line scrolls sideways, one screen row per line, and a row whose line continues past the right edge ends in a highlighted `>` (reverse video). View > Word Wrap turns on soft wrap for the session, and the `word_wrap` setting chooses how a session starts (off). With wrap on, a line continues on the following rows, broken after whitespace, and Up, Down, PageUp and PageDown move by screen row; Home and End stay whole-line. Files of any size still hold: a single line can be gigabytes long, so a line is laid out in independent 4 KiB blocks and finding any row costs at most one block ([WrapLayout](./src/text/wrap.hpp.skel.md#class-wraplayout)); nothing about a line's layout is computed from its start or cached.
- **Tabs:** the Tab key inserts a tab character, never spaces. Tabs display 4 columns wide by default; the width is the `tab_width` setting, changed in Options > User Settings…. The width is a display setting used by [display_width](./src/text/utf8.hpp.skel.md#function-display_width); it never changes the file. The accepted range is 1 to 16. The chosen width is remembered between sessions, globally (not per file type), in `settings.json` in the user configuration directory; see [Settings](./src/app/settings.hpp.skel.md#class-settings) and [settings_file](./infra/storage.iac.skel.md#resource-settings_file).
- **Settings:** user settings are described by one schema table in the code ([setting_specs](./src/app/settings.hpp.skel.md#function-setting_specs)): key, type, range, default, label and help text. The loader, the User Settings panel ([SettingsView](./src/ui/settings_view.hpp.skel.md#class-settingsview), Options > User Settings…) and the Options menu are all generated from it, so a new setting is one new row. A change in the panel is saved to `settings.json` and applied to the running session at once. The View menu toggles are per-session: their starting values are settings, and flipping one in the View menu is never saved. `settings.json` also records when each setting was last changed, and the Options menu lists the five changed most recently under User Settings… for quick changes.
- **Fatal signals:** a file truncated by another program while mapped raises SIGBUS. That crash risk is accepted: the signal handler restores the terminal and re-raises ([file_map](./src/platform/file_map.hpp.skel.md)).

## Cross-cutting: files of any size

1. **Open** maps the file with [MappedFile](./src/platform/file_map.hpp.skel.md#class-mappedfile) and seeds the piece tree with one piece per chunk. Each chunk's line count starts as *unknown*. Open is O(file size / chunk size) and does no I/O beyond `mmap`.
2. **Line counts** are filled in by [LineScanner](./src/text/line_scanner.hpp.skel.md#class-linescanner) in the background, which also computes the content hash in the same pass. A line query that lands in an unscanned chunk scans that chunk synchronously, which is bounded at about 1 MiB. Line numbers past the first unscanned chunk display as `…` until known.
3. **Edits** never copy original bytes. Deleted ranges are kept as piece runs for in-session undo.
4. **Search** streams over chunks and never builds a contiguous copy of the document.
5. **Save** streams pieces to a temporary file and atomically replaces the target. That needs free disk space equal to the file size. It records per-chunk line counts as it writes, so no rescan is needed afterwards. Extended attributes and ACLs are copied onto the temporary file before the swap. When atomic replacement is impossible (including when one of those copies fails), the user is asked at save time whether to write in place (not crash-safe) or cancel; see [write_atomically](./src/platform/fs.hpp.skel.md#function-write_atomically). An in-place save first stages the full new content in a temporary file under `$TMPDIR`, then copies it over the target; see [write_in_place](./src/platform/fs.hpp.skel.md#function-write_in_place).
6. **LSP** is disabled above a per-language size cap (4 MiB by default, overridable per language in `languages.json`) because `didOpen` must send the whole text.
7. **Progress.** The few operations that must run synchronously over data of any size (copying a sidecar for Save As, a prune's hash and rewrite, waiting for queued history to reach the disk) report bytes done to a [ProgressSink](./src/util/progress.hpp.skel.md#symbol-progresssink) that App injects through `DocumentOptions`; App redraws only the status line from it.
8. **External changes** to the file are detected by polling. When another program replaced the file (a new inode), the user is asked to reload, which starts a new history root, or to keep the in-memory version. When it wrote into the same file, the in-memory version no longer exists, so Reload is the only choice. When the file was deleted, there is no prompt: the status line says so, the document is kept, and the next save recreates the file. See [Document.check_external_change](./src/edit/document.hpp.skel.md#function-check_external_change).

## Cross-cutting: undo persistence trade-off

Every edit op carries its own deleted and inserted bytes. Referring to byte offsets in the original file would break as soon as the file is saved. Self-contained ops make the sidecar valid against any save point, but deleting a 5 GB range writes 5 GB to the sidecar. That cost is accepted. Large payloads are written by a background thread and referenced by offset, so they are not held in memory. See [Payload](./src/edit/undo_tree.hpp.skel.md#symbol-payload).

The sidecar holds every deleted byte for ever, until the user clears or prunes the history. Secrets deleted from a file remain recoverable by anyone who can read `<file>.history`. The sidecar is therefore created with the same permission bits as the edited file, and keeps the visible name `<file>.history` so that its existence is obvious. See [sidecar_file](./infra/storage.iac.skel.md#resource-sidecar_file). Save As copies the history into the new file's sidecar and leaves the old sidecar with the old file, so the deleted text then exists in both. Clear History… deletes the current file's sidecar (not the copies) and starts a new history; on a document with unsaved changes it first offers Save / Cancel and clears only after a successful save. The cleared history's node metadata (structure, kinds and times, never any text) stays visible in the undo-history panel, dimmed, until the session ends. Save As onto a file that already has a valid sidecar replaces that sidecar with the copy. Sidecars orphaned by renaming or deleting a file outside `mod` are never cleaned up.

**Pruning.** A prune keeps, for every leaf of the current tree, the unbroken run of recent steps leading to it, plus the current step and the latest save point whatever their age. It joins those runs under one new root, whose content is where they last shared history; each run's first step absorbs the removed steps above it, so some old text survives inside those first steps. Everything else is deleted: other trees are deleted, nothing is dimmed, and nothing is recoverable. The rule is in [UndoTree.plan_prune](./src/edit/undo_tree.hpp.skel.md#function-plan_prune). Declining the slow-load offer is never remembered.

The sidecar is fsynced once per save, never per edit, so a power failure can lose the history recorded since the last save; a process crash cannot. Payloads of up to 4 KiB are stored inline in NODE records; larger ones go to PAYLOAD records.

## Test strategy

- **Unit tests** are the one level the plan contains: one doctest executable per `tests/*_test.cpp`, built from the list in [tests/CMakeLists.txt](./tests/CMakeLists.txt.skel.md) and run by CTest. Each test stand-in states what it covers and links the units it exercises. The tests link `mod_core`, which is every source except `main.cpp`. The debug preset builds them with AddressSanitizer and UndefinedBehaviorSanitizer.
- **Real files, no timing.** Tests that need files write them under a scratch directory in the build tree, never in the source tree. Clocks are injected, and worker results are run with `EventQueue.drain`; a test that depends on timing is forbidden. A test that changes a file while a Document has it open replaces it by rename, never by truncation.
- **Interface components** (the text view, the history pane, the settings and key bindings panels, the menu bar) are tested by drawing to a `Screen` over a null terminal and reading its cells and cursor.
- **The language-server client** is tested against a scripted server, [fake_lsp_server](./tests/fake_lsp_server.cpp.skel.md), started as a real child process.
- **Left out.** No automated test drives the `mod` binary through a terminal, so [App](./src/app/app.hpp.skel.md#class-app) and [main](./src/main.cpp.skel.md#function-main) have no test; nor have [Prompt](./src/ui/prompt.hpp.skel.md#class-prompt) and [log](./src/util/log.hpp.skel.md#function-log), for which none has been written yet. [ChildProcess](./src/platform/process.hpp.skel.md#class-childprocess) is exercised only through the language-server tests, and the width-table generator is run by hand. Each of these says so in its `untested:` front matter.
